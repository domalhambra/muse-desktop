# mMac parity with Claude Code Desktop: design

Status: approved. Designed with Dom on 2026-10-23, one section at a time; Dom chose the features, the cut of row 10 and the milestone shape, and approved each section.

## Goal

mMac already matches the Electron fork: the branch `mac-m4a` ticks every item on the parity checklist in `2026-10-21-mac-app-design.md`. This spec looks past Electron to Claude Code Desktop, Anthropic's desktop app for Claude Code, and picks the features that bring mMac closer to it at the least cost. It is the input for two milestones, M5a and M5b, each with its own plan.

The source for every Desktop feature is the official documentation at `code.claude.com/docs`. Each feature below cites its page. The source for what Muse can do is the SDK the fork already uses, `@muse-code/sdk` 1.4.7, read in `node_modules/@muse-code/sdk/dist/src/msp.d.ts`. Line numbers below are from that version.

## Decisions

| Decision                                                                                                    | Why                                                                                                                                                                                            |
| ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ten features in two milestones: eight that reuse what exists (M5a), two that need new backend modules (M5b) | Dom's call. The eight each need one Muse call or event, one MuseKit rule and one view. The two need their own Vitest suites, so they wait for the quick wins to land.                          |
| New Muse calls go into `src/main/muse-host.ts`, after `listWorktrees`                                       | The fork already extends that file for worktrees and the experimental grant. One place, one pattern, and `tests/unit/headless-parity.test.ts` keeps the two front doors equal.                 |
| Muse's own approval-mode names show in the Mode menu                                                        | One term per thing. Desktop's Manual, Accept edits, Plan, Auto and Bypass name different policies. Muse's four modes are closed: a client selects one, it cannot define one (`msp.d.ts:2012`). |
| The session shell is `!` in the composer, not a terminal pane                                               | Muse runs the command in the session's folder and the transcript keeps the result (`session/userShell`). A PTY pane is a later milestone, if ever.                                             |
| The preview pane takes a URL; it does not detect dev servers                                                | Muse has no `launch.json` equivalent. A URL field and a per-project memory cover the Astro properties.                                                                                         |
| `cron-parser` is the one new dependency, recorded in `docs/compatibility.md`                                | A cron parser with its tests is more code than the rest of scheduled tasks.                                                                                                                    |
| The PR monitor sends the Auto-fix prompt to the conversation; it does not run its own agent                 | Muse is the agent. mMac composes the prompt, so the rule is pure and tested.                                                                                                                   |
| Cloud sessions, Remote Control and split view are out                                                       | The first two need a service Muse lacks. Split view needs a per-window `Workspace`, a refactor of its own.                                                                                     |
| Diff line comments and view modes are out                                                                   | Dom skipped them on 2026-10-23.                                                                                                                                                                |

## M5a: the eight reuse features

Shared ground. Every new Muse call follows `listWorktrees` in `src/main/muse-host.ts`, gets a `method()` in `src/headless/backend.ts`, a typed call in `mac/Packages/MuseBackend/Sources/MuseBackend/Methods.swift`, a row in `tests/unit/headless-parity.test.ts` and a scripted reply in `mac/Fixtures/fake-backend.mjs`. Every new event is an `AppEvent` in `src/shared/protocol.ts`, folded by the host, applied by `Workspace.apply`. Every rule is pure Swift in `MuseKit` with a `swift test`. Views reuse the transcript, composer, inspector and sheet views M1 to M4a built. Where the table names a file that exists only on `mac-m4a` (`ComposerRules.swift`, `ComposerMenus.swift`, `HelpSheet.swift`, `WindowSheets.swift`, `Workspace+Conversations.swift`), M5a's branch is cut after `mac-m4a` merges.

## M5b: the two backend modules

Both get a new file under `src/headless/`, their own Vitest suite, typed Swift calls, MuseKit rules and one view each. Neither touches `src/main/`.

### Scheduled tasks

Desktop keeps a Scheduled page: tasks with a name, instructions, folder, trigger (Hourly, Daily, Weekdays, Weekly, Manual, or a cron expression at one hour or more), permission mode and model, plus Run now, Active or Paused, a history with skip reasons, and Delete. It checks every minute while the app is open, skips runs while the computer sleeps, and runs one catch-up for the latest missed time within seven days.

| Part      | Design                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Backend   | `src/headless/schedule.ts`: a `schedules.json` store in mMac's data folder, a one-minute timer, `cron-parser` for the custom trigger. A due task calls the existing `create` with its model and worktree flag, then `set-approval-mode` from M5a, then `send` with the prompt. One scheduled run at a time; a task due while another runs records a skip with its reason. At start, and after a gap longer than two minutes (a wake), one catch-up per task for the latest missed time within seven days. History keeps the last 50 runs per task. |
| Methods   | `schedule-list`, `schedule-save`, `schedule-remove`, `schedule-run`, `schedule-enabled`. A `schedule-run-started` event names the task and its session.                                                                                                                                                                                                                                                                                                                                                                                            |
| MuseKit   | `ScheduleRules`: validation (name, prompt, folder, the one-hour floor for cron), preset to cron, "next run" text. `Workspace+Schedules` holds the list and the latest run per task.                                                                                                                                                                                                                                                                                                                                                                |
| App       | A Settings pane "Scheduled": the list, the form, Run now, an Active switch, the history, Delete behind an Ask. A sidebar group "Scheduled" with one row per active task; a click opens its latest run. A completion notice "Scheduled task <name> finished" rides the existing notifications.                                                                                                                                                                                                                                                      |
| Proof     | `tests/unit/headless-schedule.test.ts` with a fake clock and the fake `MuseHost`: due detection, one run at a time, the catch-up picks the latest missed time, the history cap, the cron floor. MuseKit: `scheduleRulesValidateAndDescribeTheNextRun`. A fake-backend UI step lists two tasks, pauses one and runs the other.                                                                                                                                                                                                                      |
| Not built | Keep-awake, a per-task "always allow" memory, the on-disk `SKILL.md`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

### Pull request monitor

Desktop shows the session's pull request in the Changes card with CI status, and a menu with Auto-fix and Merge when ready. It needs `gh` installed and signed in.

| Part    | Design                                                                                                                                                                                                                                                                                                                                                                |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Backend | `src/headless/pull-request.ts`: `pr-status` runs `gh pr view --json` in the conversation's folder (worktree or project) and returns number, title, URL, state, review decision and each check's name and conclusion. `pr-merge-when-ready` runs `gh pr merge --auto --squash` after an Ask. A missing or signed-out `gh` returns a clear message, and the poll stops. |
| MuseKit | `PullRequestRules`: the summary (passing, failing, pending), the poll decision (every 60 seconds while Changes shows and a PR exists), and the Auto-fix prompt, which names the failing checks and asks Muse to read their logs with `gh` and fix them. `Workspace+PullRequest` holds the status.                                                                     |
| App     | A PR card at the top of Changes: title, number, checks with icons, Open on GitHub, Auto-fix (sends the prompt to the conversation), Merge when ready. On merge, a toast "PR merged" with an Archive button. No auto-archive preference.                                                                                                                               |
| Proof   | `tests/unit/headless-pull-request.test.ts` with a fake `gh` script on `PATH`: parsing, missing `gh`, not signed in, the merge command line. MuseKit: `checksSummarizeToPassingFailingPending`, `theAutoFixPromptNamesTheFailingChecks`. A fake-backend UI step shows a card with one failing check.                                                                   |

| Feature         | Benefit of building                                        | Cost       | Risk of leaving                                                         |
| --------------- | ---------------------------------------------------------- | ---------- | ----------------------------------------------------------------------- |
| Scheduled tasks | Recurring Muse work runs without Dom's hand, on his files  | Three days | Nothing in mMac runs unattended; recurring work needs launchd or memory |
| PR monitor      | CI results, the fix request and the merge, all inside mMac | Two days   | Failures are found on GitHub, and the fix request is typed by hand      |

## Testing

The gate is "Prove a change" in `docs/changing-things.md`, unchanged, plus the new suites named above. Every new launch sets `HOME`, `XDG_CONFIG_HOME` and `MUSE_HOME` to a temporary folder (invariant 4 in `CLAUDE.md`). The fake backend gains the new methods and events at the protocol number both sides share; a new message shape raises `HEADLESS_PROTOCOL` and `backendProtocol` together.

| Layer         | Proves                                   | How                                                                                                 |
| ------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------------- |
| The host      | Each new Muse call and fold              | `tests/unit/muse-host.test.ts` against the fake connection                                          |
| The backend   | Each new method, and the two M5b modules | `tests/unit/headless-backend.test.ts`, `headless-schedule.test.ts`, `headless-pull-request.test.ts` |
| Method parity | No method exists in one front door only  | `tests/unit/headless-parity.test.ts`                                                                |
| `MuseBackend` | The new typed calls and models decode    | `swift test`                                                                                        |
| `MuseKit`     | Every rule above                         | `swift test`                                                                                        |
| The app       | The main flows                           | `xcodebuild test`: the steps added to the echo and fake-backend UI tests, three runs in a row       |

## Milestones

Each milestone is one PR from its own branch into the fork's `extensions` branch, cut after `mac-m4a` merges. Dom merges.

| Milestone             | Holds                                                                   | Done when                                                                                                                    |
| --------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| M4b                   | The proof of M2 to M4a: the UI tests three times, the live isolated run | Already planned in `2026-10-22-mmac-m4a.md`. Comes first.                                                                    |
| M5a: session controls | Features 1 to 8                                                         | Both `swift test` runs, the host, backend and parity tests, and the echo and fake-backend UI tests pass three runs in a row. |
| M5b: services         | Features 9 and 10                                                       | The two Vitest suites, their MuseKit tests and the fake-backend UI steps pass.                                               |

Recommended order inside M5a, by value over cost: permission modes, session shell, the context card with the changes indicator and the Tasks pane, side chat, keyboard parity, the file context menu, the subagent list, the preview pane. Inside M5b: scheduled tasks first.

## Out of scope

Cloud sessions, Remote Control, mobile push, split view, diff line comments, view modes, computer use, the iOS Simulator pane, Dispatch, SSH and WSL environments, connectors, a PTY terminal pane, dev-server detection, keep-awake, and auto-archive on merge.

## Open questions

For the plans, not this spec:

- The wording for the four approval modes in the Mode menu. The M5a plan probes Muse's own TUI for its labels and descriptions.
- Whether `session/sideChat` seeds the side with the main thread or opens empty. The SDK says "the side opens empty" and names an open issue on inherited turns (`msp.d.ts:2078`). The plan probes it with the real CLI.
- Whether `userShell` needs the `experimentalApi` grant the host already requests, or only its own capability.
- Whether a `subagent` item can be stopped from a client. The spec builds no stop control; the plan may add one if the SDK offers it.
