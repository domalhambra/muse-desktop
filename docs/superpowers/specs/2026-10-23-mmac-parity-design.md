# mMac parity with Claude Code Desktop: design

Status: approved. Designed with Dom on 2026-10-23, one section at a time; Dom chose the features, the cut of row 10 and the milestone shape, and approved each section. Amended the same day: Dom added usage and limits (features 11 to 13) to M5b and approved that design one section at a time. Later the same day, Dom approved change cards as the main view of feature 10. M5a was built on 2026-10-23 and M5b on 2026-10-24; M5b's UI test runs and live checks are pending.

## Goal

mMac already matches the Electron fork: the branch `mac-m4a` ticks every item on the parity checklist in `2026-10-21-mac-app-design.md`. This spec looks past Electron to Claude Code Desktop, Anthropic's desktop app for Claude Code, and picks the features that bring mMac closer to it at the least cost. It is the input for two milestones, M5a and M5b, each with its own plan.

The source for every Desktop feature is the official documentation at `code.claude.com/docs`. Each feature below cites its page. The source for what Muse can do is the SDK the fork already uses, `@muse-code/sdk` 1.4.7, read in `node_modules/@muse-code/sdk/dist/src/msp.d.ts`. Line numbers below are from that version.

## M5b: usage and the two backend modules

#### Change cards

Dom does not follow Git, so the monitor's main view shows each pull request as a change card on a delivery track. Branches, commits and diffs stay one click away, under "Show details". The cards reuse the monitor's PR status and CI data.

The plain model, in the app's Help text: the project has a master copy. A pull request is a proposed edit on a draft copy. Accepting it merges the draft into the master copy.

Each card, top to bottom:

1. **One sentence:** what changes for Dom, for example "mMac now shows your usage limits in the footer". It comes from the PR's title and body, never from code.
2. **Before and after:** a screenshot or a short visible example, when the PR body has one. Otherwise the part is left out, with no word about code.
3. **The track:** Drafted → Checked → Ready for you → Accepted → Live, with the current step lit.
4. **A risk light:** green, amber or red, with one line of reason, for example "touches only docs" or "changes how mMac talks to Muse".
5. **Depends on:** "Accept PR 9 first", drawn as an arrow between the two cards.
6. **Two buttons:** Accept merges the PR. Ask why opens a plain-language explanation in a side chat (feature 5).

## Out of scope

Cloud sessions, Remote Control, mobile push, split view, diff line comments, view modes, computer use, the iOS Simulator pane, Dispatch, SSH and WSL environments, connectors, a PTY terminal pane, dev-server detection, keep-awake, and auto-archive on merge.

## Open questions

For the plans, not this spec:

- The wording for the four approval modes in the Mode menu. The M5a plan probes Muse's own TUI for its labels and descriptions.
- Whether `session/sideChat` seeds the side with the main thread or opens empty. The SDK says "the side opens empty" and names an open issue on inherited turns (`msp.d.ts:2078`). The plan probes it with the real CLI.
- Whether `userShell` needs the `experimentalApi` grant the host already requests, or only its own capability.
- Whether a `subagent` item can be stopped from a client. The spec builds no stop control; the plan may add one if the SDK offers it.
- Whether Muse 1.4.12 reports `usage/changed` for Dom's provider. The SDK has the method; the login decides whether data comes back. The M5b plan proves the feature against the fake backend, and the live run checks the real login.
- When a PR into a branch other than the default branch counts as Live. The fork's PRs go into `extensions`, while `main` mirrors upstream, so by the rule above they stop at Accepted. The M5b plan decides whether `extensions` counts as the fork's master copy, as a per-project setting. Answered in M5b: no setting. Live means a merge into the default branch or a successful deployment, so the fork's PRs show "Accepted into extensions" and leave Live unlit (`docs/decisions.md`, 2026-10-24).
